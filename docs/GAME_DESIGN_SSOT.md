# もぐもぐ日記 — ゲーム・カード制作仕様（SSOT）

> **SSOT = Single Source of Truth（唯一の正本）**  
> **状態：承認済み仕様 / 最終更新：2026-10-11**  
> **対象：ガチャ報酬、キャラクターデザイン、レアリティ、カードの作画・合成、ゲーム進行、保存ルール。**

## 0. この文書の位置づけと変更管理

1. **このファイル `docs/GAME_DESIGN_SSOT.md` だけが、ゲーム・カード制作仕様の唯一の正本（SSOT）。** READMEは概要、過去の議論・試作は履歴、ソースコードは現在の実装状態を示す。これらが矛盾した場合、**新しく何を制作するかの判断ではこのSSOTを優先**する。
2. **承認済みの美術方針を実装都合で変更しない。** 特に、イラスト品質を下げて簡易SVGキャラや絵文字に置き換えることを禁止する。技術的な代替策が必要なら事前にユーザーへ説明し、承認を得る。
3. 仕様変更はユーザーとの合意後にこの文書へ反映し、その後にコード・画像アセットへ適用する。未承認の提案は「検討中」、動くだけのものは「試作」、完成品質が確認されたものだけを「承認済み」と呼ぶ。
4. **技術的に描画・合成できることと、カードのイラスト品質が合格であることは別。** コード上の表示テストだけで「カード完成」と報告しない。
5. 過去の不承認試作資料は、誤った制作方針を再び参照しないよう削除済み。旧資料のうち承認済みの決定事項のみ本書に統合した。過去の会話や試作は新しい制作ルールの根拠にしない。
6. アプリ**全体**の配色・レイアウトなどの仕上げは主要機能の実装後にまとめて行う。ただしカードアートの品質確認は先行する。

## 1. ゲームの目的と報酬設計

- 目的は**食事を記録する習慣を楽しく続けること**。食べる速さ・時間の長短、過剰な食事回数、間食回数を報酬の有利不利に結びつけない。
- 家族3プロフィール（いちか／じゅんちゃん／さとばぁば）それぞれ独立したゲーム進行を持つ。
- **無料ガチャは1日1回**。追加ガチャはゲーム内コインかガチャ券で引ける。**現時点で課金要素なし**。
- ログインボーナス：1日1回 **10コイン**。
- 通常の食事記録：1日最大3回、**1食目20コイン、2・3食目各10コイン**。**おやつは対象外**。記録時間の長短で報酬は変えない。
- 連続記録報酬：**3日で30コイン、7日でガチャ券1枚、14日で2枚、30日で3枚**（現行初期設定）。
- 追加ガチャ：**100コイン／1回**、または**ガチャ券1枚／1回**。
- 同じキャラクターの重複獲得は**レベルアップ**に使う。レアリティ自体は上昇しない。所持枚数 **1／2／4／7／11枚** で **Lv.1／2／3／4／5**。
- 重複による成長演出・外見の追加は可能だが、キャラクターの本来の作画品質を下げてよい理由にはならない。

## 2. キャラクター・世界観

- 基本は**食べ物 × 偉人・芸術家・歴史・文化・象徴**。食べ物の姿をした人格・人物風の姿に食べ物の意匠・中間型の**混合デザイン**をキャラごとに選ぶ。
- 偉人の「好物」に限定しない。例：ニュートンとりんごの**逸話・象徴**、絵画のモチーフ、地域とのゆかり。**史実と創作の区別**を付け、好物と断定できないものを好物と書かない。出典情報は背景に詰め込まず図鑑の説明へ。
- **特に日本の芸術家を厚く**扱う。海外の芸術家・その他偉人もバランスよく収録。
- オムライスは独立した豊富なシリーズ。**R〜SSRへ複数バリエーション**を配置する。
- **一般公開・将来のアプリ化を見据え、個人の名前をカードの表示名に使わない。** SSRの公開表示名は **「きらめきオムライス姫」**。内部ID `omu_ichika_ssr` は所持データ互換性のため維持し、新しい表示・公開文言へ展開しない。
- 実在人物・作品を着想源にしても、他社のキャラクターや特定カードの固有デザインを複製しない。

## 3. レアリティと抽選仕様

| レア度 | 排出率 | 作画・豪華さの基準 |
|---|---:|---|
| **N** | **72%** | 高品質なキャライラスト＋ごく簡素な紙風**背景画像**・細枠、ホロなし |
| **R** | **20%** | Nより明確に華やかな色・模様・小さな装飾、ただし**派手すぎない**。基本ホロなし |
| **SR** | **6%** | キャラの魅力を維持しつつ装飾追加、薄いパール・軽いホロ反射 |
| **SSR** | **1.75%** | **圧倒的に豪華**。専用の細密イラスト、華やかな金装飾・世界観のある背景・強い虹色ホログラム。**フルアート生成可** |
| **UR** | **0.25%** | **隠し要素・別格の専用アート**。SSRを超える特別演出・背景・フレーム。**フルアート生成可** |

- レアリティは**N → R → SR → SSR → UR**の順に明確に豪華になる。**NとRの差**は色・背景とフレームの工夫で読み取れるようにし、SRから光沢が分かるようにする。
- 実際の食品の珍しさ、子どもにとっての好物度、偉人との関係の特別さをレア評価の参考にするが、ゲームとしての演出上の例外を認める。
- URは**存在を原則秘密にする**。未所持状態の通常図鑑・公開UIで名前・シルエット・総数・排出率・存在を明かさない。開発用プレビューのみ例外。
- URの期待値は**500回で1.25枚**。独立抽選で保証はなく、現段階で天井・救済は設けない。全レア内のキャラは現行仕様では等確率。
- 公開リポジトリにキャラマスタ・抽選コードが含まれる限り、**技術的な完全秘匿ではない**。必要なら後にサーバー抽選を検討する。

## 4. **最重要：カードの制作方式（美術仕様と実装仕様を混同しない）**

### 4.1 N・R・SR：高品質キャラ画像＋共通部品の合成

**キャラクター本体は、高品質で個性のある独立したイラストを画像生成等で制作し、透過PNG／WebPなどの画像素材として扱う。**

- 食べ物・人物の要素、表情、衣装、固有のポーズ、色、陰影、質感まで**キャラごとに描き込む**。
- **簡易SVGをプログラムで量産したキャラクター、共通素体の色替え・帽子替え、絵文字を最終イラストとして採用しない。**
- SVGを使用するのは原則、**フレーム・幾何模様・飾り・UI効果**。**背景SVGは使用しない。**ベクター形式そのものを禁止するわけではないが、簡易SVGキャラは不合格。完成イラストと同等の品質があり個別承認された場合だけ例外とする。
- **「5レイヤーで作る」は、カードをどう合成するかの技術仕様であって、キャラクターをSVGで描く指示ではない。** この区別を守る。
- 共通化するのは**背景や装飾などの部品**。キャラの個性を犠牲にして制作コストだけを下げない。

**推奨レイヤー（背面 → 前面）**

1. **背景**：**N/R/SR/SSR/URの5段階で別々の背景ラスタ画像（WebP/PNG）を用意する。SVGで背景を制作・保管しない。** Nは控えめ、Rは少し華やか、SRは物語性、SSRは豪華、URは別格。キャラ・文字・額縁を焼き込まず、共通再利用可能な背景画像だけを制作。
2. **ホロ／印刷質感**：背景の無地・余白部分を光らせる。キャラクター本体を白く覆わない。N・Rは原則なし、SRは弱め。
3. **下フレーム SVG**：輪郭・基礎額縁・装飾の土台。
4. **キャラクター透過PNG／WebP**：カードの主役となる描き込まれたイラスト。
5. **上フレーム SVG**：キャラの手前に重なる角飾り・箔・リボン等。主役を隠しすぎない。
6. **HTML／CSSテキスト**：キャラ名・レア度・レベル・種別など。後から変更できるよう画像とは分離。

この5つの絵作りレイヤー＋文字UIを、実際の**Webアプリ上で合成**する。単に各レイヤーの完成イメージを画像生成して見せるだけでは「実装」とは言わない。

### 4.2 SSR・UR：制作点数が少ないためフルアートを許可

- **SSRは現在11種類、URは3種類**の初期マスタ。ここはパーツ量産にこだわらず、**高精細で豪華な個別生成イラスト／カード全体のフルアート**を正式に認める。
- **SSRの品質基準は、ユーザー提示の「ゴッホのひまわりパン」の豪華なキラカード参考画像程度。** 豊かな陰影、緻密な造形、ひまわりや金箔・宝石・リボン・背景の情報量、強いホログラムが見て取れること。従来の単純なSVGキャラ＋斜め線背景は不合格。
- SSRは**かなり派手でよい**。Rから派手にしすぎず、SSRに明確な格上感を持たせる。
- URはSSRを超える専用表現を許すが、**未発見状態では存在を示唆しない**。
- フルアート画像を使う場合も、可能な限り**カード名・所持レベル・レア度などの情報をアプリ側で保持**する。フレームや背景まで画像化してよく、SSR/URだけ5レイヤーを強制しない。
- フルアート使用とレイヤー構造の共存が可能な設計にする。今後の差し替えを容易にするためカードIDとゲームデータは維持する。

### 4.3 ホロの意味

- ユーザーが求める「ホロ」は、単に**一瞬キランと走る反射アニメーション**だけではない。
- **背景の無地・余白に、現物のトレーディングカードのような細かなラメ・多層反射・虹色箔・光の粒が見える状態**を指す。必要なら画像化したホロ模様や生成フルアートを使う。
- CSS・SVG・透明素材は手段。**安っぽい単純な線・均一なキラ粒だけで完成としない**。
- SSR/URではホロの華やかさを十分確保する。キャラの表情や造形を光で潰さない。

## 5. 品質確認・実装時の必須手順

1. レア度ごとの**美術基準**を最初に確認する（NとRの差、SRの中間感、SSRの圧倒的な豪華さ、URの別格感）。
2. **最初にN・R・SRの高品質な透過キャラ素材を確保する。** 枠やホロだけ完成していてもキャラが簡易SVGなら不合格。
3. アプリ側の背景／下枠／キャラ／上枠／ホロを**ブラウザで実際に合成**。SSR/URの場合は合意したフルアート方式でも可。
4. **画面上の実物**で確認する。比較画像を生成して終わらない。PC/スマホ表示、図鑑一覧と拡大表示、Rが派手すぎないか、SSRが十分豪華かを確認する。
5. **ユーザーが品質を了承してから量産**する。承認済み基準と違う作画手段・品質への変更は先に相談する。
6. 試作と本番・承認済みと未承認を明記する。検証用カードの存在だけで「62枚完成」と表現しない。

## 7. データ保存・公開上の制約

- `families/{familyId}/games/{profile}` のプロフィール別データをFirestoreに保存し、本人の匿名認証プロフィールへの書き込みを制限する。
- ガチャ／コイン／重複獲得はFirestoreトランザクションで扱う。ただしブラウザ側抽選なので、**不正改ざん防止・UR秘匿は完全ではない**。商用化時は信頼できるサーバーでの抽選・報酬検証を検討する。
- Firebaseセキュリティルールを変更した際は、リポジトリの `firestore.rules` の更新だけでなく、Firebase Console側への適用が必要。
- **家族コード、個人の食事記録、認証情報をGitHubへ保存しない。**

## 9. 背景制作ルール（2026-10-11追記）

- 背景画像はラスタ形式（**PNG/WebPを用途に応じて利用**）。WebPは圧縮画像であり、SVGではない。カード内の表示対象が背景であればすべてこの形式を守る。
- 既存の背景SVG4件はSSOTと不一致のため**削除済み**。**フレーム用SVG14件は完成済み部品として保持**する。
- **N/R/SR/SSR/URの5種類を先に作り、キャラ本体がなくても背景とフレームのみでレア差を比較できるようにする**。
- 背景素材には**キャラ・文字・レアバッジ・上下枠を混在させない**。SSRやURのフルアートを別途制作する場合のみ例外とする。
- キャラクター画像が未制作なら空欄を維持する。簡易SVG・共通素体を埋め戻さない。
- 以前の複数SSOT/過去の試作資料は削除し、今後は本書だけを参照する。誤実装を生みやすい古い記述・参照リンクをREADMEなどにも残さない。
